# 天津 AI 旅行规划平台

一个能真跑起来的 AI 旅行规划 Agent：用户填需求 → LangGraph 编排生成多日行程 →
用自然语言多轮调整（"第二天轻松点""加顿火锅"）→ 秒级局部重规划。

不是 demo 壳子：**80 条天津本地知识语料**（景点/美食/酒店/交通/避坑）、
**混合检索**、**冲突校验**、**路线优化**都是真实实现，行程可直接照着走。

## 三、核心设计：每一处为什么要这么做

### 3.1 LangGraph 状态图 —— 校验不通过能带着问题回去重做

```
retrieve → draft → validate ─┬─(有硬伤、还能返工)→ draft        ← 回头边
                             ├─(有硬伤、返工用尽)→ repair ─┐
                             └─(没问题)──────────────────┤
                                                        └→ optimize → finalize
```

关键在 **repair 这条分支**：让模型改两遍它可能还改不对（实测过：周一闭馆的博物馆
反复排在周一）。返工次数用尽后，用规则硬修——换成同片区当天开放的景点。
宁可输出一份机械但没毛病的行程，也不能让用户到门口吃闭门羹。

### 3.2 防幻觉：三道闸门

1. **参考资料硬约束**：提示词明确"只能从资料里选，编造名称一律重做"
2. **校验节点查名字**：景点名不在知识库 → 判为 error，触发返工
3. **别名归一**：模型爱写简称（"意风区""天博""煎饼果子"），先归一到标准名再判断，
   不冤枉模型的正确意图，也避免误判成幻觉

### 3.3 混合检索：为什么不全靠向量

- **关键词路（权重 0.45）**：擅长专名。搜"天津之眼"，字面命中必须排第一。
  纯向量对专名反而容易飘到别的摩天轮上。
- **向量路（0.55）**：擅长模糊意图。搜"带老人走得慢一点"，字面上跟任何景点都不重合。
- 中文不装 jieba，用**字符二元组**算覆盖率——几十条短文本场景下足够准，少一个依赖。

### 3.4 路线优化：模型排的顺序常常是想到哪写到哪

实测模型会排出"上午和平区 → 中午南开区 → 下午又回和平区"。
`optimize_route` 用**贪心最近邻 + 2-opt** 重排（一天最多 5-6 个点，不需要最优解，
毫秒级返回），再把通勤分钟数实打实算进时间线。

### 3.5 多轮对话：为什么不能每次全量重生成

| | 全量重生成 | 局部重规划 |
|---|---|---|
| 耗时 | 30 秒 | **0.1 秒** |
| 成本 | 一次完整 LLM 调用 | 多数情况零 LLM（规则命中） |
| 风险 | 把用户满意的部分也改掉 | 只动受影响的那一天 |

意图识别**规则优先、模型兜底**："第二天轻松点""改成打车"这种高频说法用正则秒回，
只有"我妈腿脚不好后半程别爬山了"这种才交给模型。

## 五、技术选型：为什么有些东西没用

| 原技术栈 | 本项目 | 原因 |
|---|---|---|
| MySQL | **SQLite** | 本机没装 MySQL 服务。存储层单独一个文件，换 SQLAlchemy+MySQL 业务代码不动 |
| Redis | 进程内缓存 | 单机 demo 用不上分布式缓存，embedding 落磁盘缓存已够 |
| Celery | 同步调用 | 行程生成本就是同步等待的场景，没有异步任务需求 |
| 高德/百度地图 API | **Haversine 直算** | 没有 key 且要限频。判断"远不远、会不会跨区折返"这个目的，经纬度直算够用，且离线可复现 |
| pgvector | JSON 文件存向量 | 80 条向量，全量加载内存算余弦相似度 <1ms，不需要向量数据库 |

这些取舍不是偷懒，是**在有限条件下把功能做完整**。面试时要能主动讲出来。

## 六、面试话术（数字化转型管培生方向）

**Q：这项目解决什么业务问题？**
> 自由行用户做攻略的平均耗时是 3-5 小时，还要在小红书、马蜂窝之间反复横跳，
> 最后排出来的路线经常跨区折返、周一吃闭门羹。这个平台把规划时间压到 30 秒，
> 并且用校验规则把"闭馆""超时""跨区折返"这几类高频错误在系统侧就拦掉。

**Q：为什么不直接调一次大模型生成行程？**
> 试过，三个问题：一是模型不知道天津本地细节会编；二是排出来的顺序不考虑地理距离，
> 实测出现过上午和平区、下午南开、晚上又回和平；三是改一个字要整份重生成，等 30 秒。
> 所以拆成检索、生成、校验、优化四个节点，分别解决知识、结构、正确性、效率。

**Q：怎么衡量效果？有没有量化？**
> 三个数：一是生成耗时 30 秒 vs 人工 3-5 小时；二是多轮调整 0.1 秒 vs 全量重生成 30 秒，
> 且 6/6 的常见说法走规则不花钱；三是冲突拦截——校验规则会在输出前抓到闭馆、
> 超时、跨区三类硬伤，实测 3 天行程平均触发 1-2 次返工或规则修复。

**Q：幻觉怎么控制的？**
> 三道闸门：提示词里限定只能从资料选、校验节点比对知识库名称、别名归一层避免误杀简称。
> 兜底还有 repair 节点——模型改两遍还不对就用规则硬换景点，保证交付的一定能执行。

**Q：这个项目体现什么数字化能力？**
> 不是"会不会调 API"，而是**把业务规则翻译成系统约束**的能力。
> 比如"周一闭馆"是业务知识，我把它变成 open_hours 字段 + 校验规则 + 自动替换策略；
> "别跨区折返"是经验，变成片区划分 + 距离矩阵 + 2-opt 重排。这是数字化的核心动作。

**Q：如果要上线还差什么？**
> 四件事：换 MySQL + Redis 扛并发；接真实地图 API 拿精确路线和实时路况；
> 行程生成改流式输出（SSE），30 秒白屏体验太差；前端用 uni-app 打包成小程序。
